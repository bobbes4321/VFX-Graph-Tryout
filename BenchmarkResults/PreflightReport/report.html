How to read the costs

When the GPU is the constraintCompare GPU deltas and their repeat ranges at the required visual density. Check Overdraw and 1440p. A CPU-cheaper technique can still have a higher GPU cost. Compare 1-segment straight ribbons with 16- or 32-segment curved ribbons only when that visual tradeoff is acceptable.
When gameplay CPU is the constraintCompare main and render thread times as well as the presentation bridge. The bridge includes the completion wait for renderer-specific Burst jobs and API submissions. For particle jobs it includes the last completed particle callback duration. It excludes later engine simulation, culling and render-thread work. Command production and consumption are common to every technique, including the baseline.
VFX instance count and graph authoring

Shared VFX uploads 64 bytes per line and reads them in a Custom HLSL graph block. Per-line VFX exposes Start, End, Tint and Shape; each pooled object receives those values. The same graph is tested with instance batching disabled and automatic batching enabled. Shared graph capacity is the next power of two at or above the particle count (minimum 16). Per-line capacity is the next power of two at or above segment count (minimum 8). This avoids benchmarking a giant fixed-capacity shared graph at tiny workloads.

Shuriken configurations and visual differences

Shared billboards and per-line billboards receive CPU/Burst-generated particles through SetParticles. Shared mesh particles use the same segment quad, with GPU instancing either off or on. The particle-job path writes directly into Shuriken's native particle arrays via IJobParticleSystemParallelFor, without copying a full particle array every frame. SetParticles paths pause simulation for explicitly positioned, persistent particles. The particle-job path remains playing to receive OnParticleUpdateJobScheduled, and explicitly schedules/completes its Burst job in that callback. Automatic movement and emission are disabled. GPU instancing accelerates rendering, not CPU particle simulation. Color32 introduces color quantization; the common HDR beam texture supplies brightness.

All methods use the same endpoints, curve formula, segment budget, additive profile texture, camera, arena and post-processing. LineRenderer uses joined strips and an eight-key color gradient; the other paths use overlapping independent quads. Billboard orientation is engine-generated. These are practical quality-matched comparisons, not pixel-identical implementations. The 1-segment tests intentionally reduce curvature quality.

Reproducibility and limitations

VSync and frame caps are disabled. Each repetition randomizes technique order within a configuration. Each configuration has its own no-lines baseline with identical native command work and scene. Static paths avoid redundant uploads and pause VFX simulation after initialization. Moving updates all endpoints. Churn stops half the slots for 15 of every 30 frames and reuses pooled objects with new generations. Shared systems keep inactive slots allocated and invisible. Overdraw concentrates long, wide lines in the same screen region.

FrameTimingManager reports delayed whole-frame GPU/CPU timings. Only fresh timing stamps are used. Unsupported counters remain missing, never zero-filled. GC and batch recorders can be unavailable in release players. API input bytes are values submitted to Unity APIs, not measured bus traffic. Total used memory is process-wide and allocator-dependent. Setup/teardown, shader first-use compilation, asset loading and pool creation are excluded from steady samples; setup is recorded separately. Teardown in the raw run refers to the previously configured pool. Background applications, drivers, presentation and clocks can introduce noise. Three runs indicate repeatability, not a universal confidence interval.
